# WhatsApp phone verification — proof of concept

**Status: PoC, NOT production-ready.** It becomes a candidate for production only after a real
Meta test-number run shows the webhook sender can be matched to the entered number (step 5 below).

## What it does

1. Admin panel → **WhatsApp test (PoC)** → enter a number → **Verify with WhatsApp**.
2. Edge Function `wa-verify-start` checks the Supabase JWT, normalises the number to E.164, creates a
   random 120-bit single-use code (10 min), stores **only its SHA-256 hash** bound to the user + number,
   and returns a `wa.me` link with the code prefilled.
3. The user sends that message from WhatsApp to FreightLink's WhatsApp Business number. FreightLink
   sends nothing (no SMS, no outbound WhatsApp).
4. Meta calls Edge Function `wa-webhook`. It verifies `X-Hub-Signature-256` over the raw body with the
   App Secret, ignores status updates and other events, extracts the code, and calls `wa_poc_inbound`.
   That call is one transaction keyed by Meta's message id, so retries are no-ops.
5. Result: **verified** only when the code matches, it is unexpired and unused, and `messages[].from`
   contains a phone number equal to the entered number. If Meta sends only a BSUID, or nothing usable,
   the result is `no_phone_in_webhook` and the challenge is **not** consumed.

Not changed: registration, login, roles, routing, profile creation, `public.users`. A verified result
lives only in `wa_verify_challenges`. By default only admins can start a test, and the server
enforces this.

## Manual setup (you do this — never paste secrets into chat or code)

### 1. Supabase — database
SQL editor → run `supabase/migrations/0030_whatsapp_verify_poc.sql`.
It only adds new objects and can be run again safely.

### 2. Supabase — secrets
Dashboard → Edge Functions → **Secrets** (`https://supabase.com/dashboard/project/<PROJECT_REF>/functions/secrets`):

| Name | Value |
|---|---|
| `META_APP_SECRET` | `<META_APP_SECRET>`: Meta App → App settings → Basic → App secret |
| `WA_WEBHOOK_VERIFY_TOKEN` | `<LONG_RANDOM_STRING>` that you invent (40+ characters) |
| `WA_PHONE_NUMBER_ID` | `<PHONE_NUMBER_ID>`: Meta App → WhatsApp → API Setup |
| `WA_BUSINESS_NUMBER` | `<+BUSINESS_NUMBER>`: the number users message (test number for the PoC) |
| `WA_POC_ALLOW_ALL_USERS` | optional, `true` lets non-admins test (default: admins only) |

`SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are injected by Supabase. They are
never put in Flutter.

### 3. Supabase — deploy the two functions
**Dashboard:** Edge Functions → Deploy a new function → Via Editor.
- Name `wa-webhook`: paste `docs/whatsapp_poc/wa-webhook.dashboard.ts`, deploy, then in the function's
  settings turn **Enforce JWT verification OFF**. Meta sends no Supabase JWT; the Meta signature is
  checked instead.
- Name `wa-verify-start`: paste `docs/whatsapp_poc/wa-verify-start.dashboard.ts`, keep JWT verification **ON**.

**Or CLI:**
```
npx supabase functions deploy wa-webhook --no-verify-jwt --project-ref <PROJECT_REF>
npx supabase functions deploy wa-verify-start --project-ref <PROJECT_REF>
```

### 4. Meta — webhook
Meta App (type Business) with the WhatsApp product:
1. WhatsApp → API Setup: note the **Phone number ID** (step 2). If the test number asks for it, add your personal
   WhatsApp number to its allowed recipient list.
2. WhatsApp → Configuration → Webhook:
   - Callback URL: `https://<PROJECT_REF>.supabase.co/functions/v1/wa-webhook`
   - Verify token: the same `<LONG_RANDOM_STRING>`
   - **Verify and save**, then subscribe the **`messages`** field.
3. If messages don't arrive, check that the WhatsApp Business Account is subscribed to the app.
   - Check: `GET https://graph.facebook.com/<API_VERSION>/<WABA_ID>/subscribed_apps`
   - Subscribe: `POST` to the same URL, with your own access token.

### 5. Test (this is the actual PoC answer)
1. Publish the app (GitHub build), sign in as admin → Admin panel → **WhatsApp test (PoC)**.
2. Enter **your own** WhatsApp number → *Verify with WhatsApp* → *WhatsApp-ı aç* → send the message unchanged.
3. The card shows the result and **"Webhook-da göndərən"**: `telefon nömrəsi var` or `yalnız BSUID`.
4. Supabase → Edge Functions → `wa-webhook` → Logs shows `wa-webhook: inbound {...}`. Its `fields` say
   which identity fields Meta sent (presence only, no values).
5. Repeat:
   - from a second phone with a different entered number, to confirm `phone_mismatch`;
   - if available, from an account that has a **WhatsApp username** and has never messaged this
     business number.

Record for each run: result, `senderKind`, `fields`, and the country of the number.

## Known limits / blockers

- **BSUID / usernames (main risk).** Since 31 Mar 2026 webhooks carry a business-scoped user id. When
  a user has a WhatsApp username, Meta may **omit** `messages[].from` and `contacts[].wa_id`.
  - The number is still included when one of these holds:
    - the business number exchanged a message or call with that user in the last 30 days, or
    - the user is in Meta's contact book.
  - Whether a *first* message from a username user carries the number is not documented. Test it.
  - When it is missing, this design cannot verify, and it correctly refuses.
- **Number format.** Matching is exact (`+` + `from` = entered E.164). WhatsApp's `wa_id` can differ
  from what users type in some countries (e.g. Brazil's 9th digit, Mexico `52`/`521`, Argentina `549`),
  which causes false `phone_mismatch`. Production would need per-country normalisation.
- **Code must arrive unchanged.** Users can edit the prefilled text. An edited code gives no result,
  and nothing is stored.
- **Production needs** a verified Meta business, an approved display name and a real number. The
  PoC uses the test number.
- **Data kept:**
  - only code hashes (cleared when a code is used, expires or is replaced);
  - Meta message ids (7 days);
  - per-user rows (deleted after 1 day on the next start).
  - No message text, phone numbers from webhooks or BSUIDs are stored. Logs mask numbers.
